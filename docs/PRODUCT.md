### 聞き取りで増えた要望と、その扱い

聞き取りには、SKETCH にも ADR 020 の計画にも無い要望があった。
ADR 020 の 11 章 3 は、聞き取りの後に「優先順位を並べ替える必要があるか」を報告するよう求めている。
報告は次のとおりで、**フェーズの順番そのものを変える必要は無い**と判断した。
最優先の「ペンの描き味」は、Phase 1 のスパイク (b)(d) と Phase 2 で最初に確かめる計画になっているためである。
計画に無い要望は、下の表のとおりに扱う。★ の項目は制作シナリオの完成に関わるので、Phase 1 の出口ゲート (見積もりを置き直すとき) に、計画へ入れるかどうかをオーナーが決める。入れる場合は ADR 020 の 6 章を改訂する。

| 要望 | 扱い | 理由 |
|---|---|---|
| 本文のページが B5・600dpi (約 4,300×6,070px) | 性能の計測に、この寸法を加える (3 章) | ADR 020 の仮の性能目標は 2894×4093 が基準で、画素数が約 2.2 倍になる。合否の条件は変えず、この寸法の値も測って記録する |

## 2. 目指す体験

目標は、「高速」「低負荷」「低認知負荷」で漫画制作を進められることである (SKETCH:53-59)。

- **高速**: 起動、描画、保存、書き出し、UI 操作の待ち時間が短い。
- **低負荷**: 大きい原稿や多ページの作品でも、メモリ消費と CPU 負荷が破綻しない。
- **低認知負荷**: 画面に一度に表示する情報を減らし、今やるべき操作が自然に見える。工程ごとに表示を絞る手段は UI プロファイル (Phase 5) で、確かめ方は Phase 4 の P5 (台本の流し込みの実演と所感) とフェーズごとの実機デモである。

altpaint は「漫画向けの機能があるペイントソフト」ではなく、漫画制作の各工程を低い認知負荷でつなぐ専用の環境として作る (SKETCH:614-625)。
MVP の核は、コマ中心ビュー、テキスト流し込み、UI プロファイル、止まらない編集体験の 4 つである。

### 想定ユーザー

主な対象 (SKETCH:61-67):

- 個人で漫画・同人誌・ネームを制作する人
- レイヤーやブラシに慣れているが、既存ソフトの UI や考え方に疲れている人
- テキストからネームを起こし、コマ単位で作業を進めたい人

将来の視野に入れるが、MVP では扱わないもの (SKETCH:69-73): アシスタントを含めた分業、大量のページを扱う商業向けの作業の流れ。
スクリプトやプラグインを自作したい人は、Phase 7 のプラグインで扱う。

### 非機能要件 (SKETCH:391-399)

数値は暫定の目標で、Phase 4 の計測の後にこの表で確定する (ADR 020 の 5 章「性能目標」)。
Phase 6 で perf ジョブで測り、STATUS.md に記録する。

| ID | 要件 | 目標 (暫定) | 先に確かめる条件 |
|---|---|---|---|
| A-NFR-01 | 起動時間 | 開発機で 3 秒以内 | Phase 3 (A-PH3-03) |
| A-NFR-02 | 100 ページの作品のサムネイル一覧 | 初回 5 秒以内、再表示 1 秒以内 | Phase 4 (P1) |
| A-NFR-03 | 大きいキャンバスでのパンとズーム | フレーム時間の p95 が 16.7ms 以下 | Phase 2 (P2) |
| A-NFR-04 | バックグラウンドの書き出し中も操作が続けられる | 書き出し中のフレーム時間の p95 が 20ms 以下で、50ms を超える停止が 0 回 | Phase 4 (P3) |
| A-NFR-05 | 書き出しのときに、入力の全体を丸ごとメモリに展開しない | 100 ページの PDF を書き出している間の RSS が 2GiB 以内 | Phase 4 (P1、P3) |

性能を測るページの寸法は 2 つにする。

- **基準の寸法**: 2894×4093・10 レイヤー (ADR 020 の仮の性能目標と、スパイク (d) の条件)。合否はこの寸法で判定する。
- **制作シナリオの寸法**: 4,300×6,070・10 レイヤー (本文の B5・600dpi)。P1・P2・P3 とスパイク (d) で、この寸法の値も測って記録する。Phase 4 の計測の後に目標を確定するときは、この寸法を基準にするかどうかを決める。

メモリの仮の目標は、100 ページの作品で RSS 2GiB 以下、VRAM 1GiB 以下である (ページ単位の遅延読込が前提)。

## 4. SKETCH から変えたこと

ADR 020 と、その質問へのオーナーの回答 (ADR 020 の 10 章) で、SKETCH の内容を次のように変えた。

| SKETCH の内容 | 変えた後 | 根拠 |
|---|---|---|
| GPU 中心で、CPU はフォールバック (SKETCH:524)。将来 GPU 処理へ拡張しやすくする (SKETCH:122) | CPU のタイルを画素の唯一の正本にし、GPU は表示に使う。性能のゲートに落ちた場合だけ、描画中のストロークかページの合成を GPU に移す | Q4 |
| 描画フレームワークと UI ランタイムを内製する。Web フロントエンドの技術は採らない (SKETCH:449-453、461) | パネルの見た目は HTML と CSS で書き、Blitz で表示する。JavaScript は使わない | Q6 |
| 標準パネルは、MVP ではまず本体のモジュールとして作る (SKETCH:231) | 同梱パネルも、最初から外部パネルと同じ Wasm の仕組みで動かす | Q6 |
| プラグインは、フィルタ・入出力・テンプレート生成・バッチから始める (SKETCH:217) | パネルが先 (Phase 2 から) で、この 4 つの拡張点は Phase 7 に入れる | ADR 020 の 6 章 |
| 外部ブラシの読み込みと、PNG・PSD・PDF の書き出しは、プラグインとして作る (SKETCH:202、296) | 外部ブラシの取込 (Phase 5) と PNG・PDF の書き出し (Phase 3・4・6) は本体で作る。PSD は後回し | ADR 020 の 6 章 |
| スナップショットの差分保存とフル保存を切り替えられる (SKETCH:251、278) | 切り替えは持たない。タイルを内容のハッシュで持つので、版はタイルへの参照の集まりになり、差分とフルの区別が無くなる | ADR 020 の 5 章「保存」 |
| 保存形式は、コマ単位でも部分ロードできる (SKETCH:276) | 部分ロードはページ単位にする。レイヤーをページの座標に置くので、コマ単位のロードは持たない | Q5 |
| レイヤーの種別にテキストを含める (SKETCH:344、353) | テキストは TextObject という独立した要素として持つ | ADR 020 の 5 章「ドメインモデル」 |
| 非同期の処理に tokio を使う (SKETCH:626 など) | tokio は使わない。重い処理はジョブ (スレッドと rayon) で行う | ADR 020 の 5 章「非同期」 |

「テンプレート」(SKETCH:112-113、413) は、キャンバスサイズのテンプレート (Phase 5) とコマ割りのテンプレート (Phase 6) の 2 つとして扱う。
「制作プロファイル」(SKETCH:86、115) と「UI プロファイル」(SKETCH:88、414) は同じものとして扱い、中身はパネルの配置とパネルの設定である。
コマを主な単位にする工程は、「ネーム以降」(SKETCH:79) とする。

- DTP 級の高度な組版

## 8. スコープを削る順番

骨格を凍結した後 (Phase 5 以降) にゲートを落とした場合は、撤退せず、次の順に範囲を削って進む (ADR 020 の 6 章「撤退の手順」)。
上にあるものほど先に削る。

1. 前後のコマやページのプレビュー (Phase 6)
2. スナップの簡易表示 (Phase 6)
3. コマ割りテンプレートのタグと検索 (Phase 6)
4. パネル以外のプラグインの拡張点 (フィルタ、入出力、テンプレート生成、バッチ) (Phase 7)
5. 作品内アセット (Phase 6)
6. UI プロファイルの書き出しと読み込み (Phase 5)
7. 変形のうち回転 (移動と拡縮は残す) (Phase 6)
8. スナップショットの分岐 (コマ単位で版を保存して戻すところは残す) (Phase 6)

次のものは削らない。制作シナリオと MVP の核に当たるためである。

- ペンの描き味 (筆圧、手ブレ補正、遅延)
- 描いた内容を失わないこと (保存、undo、書き出しが、描いた内容と一致する)
- コマ割りと、コマ中心のビュー
- 台本からの縦書きのセリフの流し込み
- PNG と PDF の書き出し

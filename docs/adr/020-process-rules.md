## 8. プロセス規約

**方針と細目の境界**: 規約を運用文書 (CLAUDE.md、PR テンプレート、`.github/` の CI とスクリプト、STATUS の再開手順) に落とし込んだ後の正本を次のように分ける。境界は、各運用文書を入れた時点からその文書について効く (Phase 0 のダミー PR の試験で検査の実装を直すのに、本 ADR の改訂は要らない)。本章に書いた正規表現やパスの一覧は初期値である。止血案へ切り替えた場合は、止血案の ADR にも同じ規則を当てる。
- **方針** (本 ADR が正本): 8 章の数値 (上限・閾値・期限)、規約の追加・削除・緩め、6 章の撤退の手順の各段階 (何をどの順で行うか)。変更には本 ADR の改訂と 11 章 1 の再レビューが要る。例外として、8 章 2 の「3 本」は、Phase 1 の判定時と Phase 2 の終わりの見直し時にかぎり、オーナーが実測に基づいて調整してよい。調整した値と理由は付録 H「運用記録」(`020-appendix-audit.md`) に追記し (11 章 1 の再レビューの対象外。Q の回答の記録と同じ扱い)、CLAUDE.md の規約の節と STATUS の「運用の変更」欄の写しにも反映する。調整した後は、付録に追記した値を正本とし、本文の「3 本」は初期値として読む。Phase 1 の出口ゲートは初期値の 3 本で判定する。
- **細目** (運用文書が正本): 検査の実装 (正規表現、数えるパス、スクリプト)、git コマンドの書き方、PR テンプレートの文面。変更は通常の PR で行い、本 ADR は改訂しない。ただし、数える対象を減らす変更、免除の範囲を広げる変更、照合を弱める変更は「緩め」とみなし、方針の手続きで行う。「緩め」は、本 ADR の規則と初期値が対象とする範囲より検査を弱める変更を指す。実装が規則の意図からずれていたのを直す変更 (誤検知や検知漏れの是正) は細目とし、PR 本文に誤検知か検知漏れの実例を書く。

1. **PR の単位**: 1 課題 1 ブランチ 1 PR。手書きのソースの追加・変更行は 400 行以内 (移植 PR は 800 行以内、削除行は対象外)、変更ファイルは 15 以内。受け入れ ID か不具合 ID を 1 つ以上参照する。この 3 点は CI で検査する。検査の定義は次のとおり。
   - 行数を数えるのは手書きのソースだけとする: `*.rs`、`*.wgsl`、`*.toml` (Cargo.lock を除く)、パネルの `panel.html` と `panel.css`、`.github/` の yml と `.github/scripts/**` (gate スクリプトもここに置く)、`scripts/`。テスト (別ファイルの `tests/`、`tests.rs`、`*_tests.rs` に置く規則とする)、文書 (`*.md`、`docs/`)、Cargo.lock、生成物、バイナリ (golden 画像など) は数えない。
   - 移植 PR の 800 行は、PR 本文に `Ported-from: <legacy-final|legacy-adr019-wip>:<パス>` がある場合だけ適用する。
   - 不具合 ID は GitHub Issue の番号とする。受け入れ ID は ACCEPTANCE.md の ID (A-R1 など) とする。スパイクには A-SPK-a〜e を採番する。
   - ID は PR 本文に `Refs: A-R1` や `Refs: #12` の形で書く。CI は正規表現 `^Refs: (A-[A-Za-z0-9-]+|#[0-9]+)` に一致する行を 1 つ以上求め、A- の ID は ACCEPTANCE.md に存在することを確かめる。
   - ID の参照を免除するのは、変更が `docs/` と `*.md` だけの PR、変更が `.github/` だけの PR (CI 用のスクリプトは `.github/scripts/` に置く)、ACCEPTANCE.md ができる前の Phase 0 の PR に限る。CI は変更パスから判定し、ラベルでは免除しない。
   - 変更が `docs/` と `*.md` だけの PR は、ファイル数の上限も免除する (ADR 001〜019 の状態欄の一括更新など)。
   - メタ検査 CI は全 PR で起動する。
   - 上限の免除は、オーナーの指示で付けるラベルで行う。`size-exempt` は行数とファイル数の両方を、`files-exempt` はファイル数だけを免除する。`size-exempt` は Phase 2 の撤去 PR と撤退時の復元 PR に、`files-exempt` は Phase 2 の骨格 PR に限って使う (6 章)。
2. **レビュー待ちの上限**: オーナーのレビュー待ちの PR が 3 本 (初期値。8 章冒頭の例外の時期にかぎりオーナーが調整できる) になったら、エージェントは新しい実装を止め、調査と下書きだけを行う。本数に数えないのは「記録だけの PR」、すなわち STATUS の更新 (8 章 11 の欄のうち「運用の変更」、「再開手順」、「現況」の週次の比率と新しく green になった受け入れ ID の数、試行期間の実測値と見積もりの計算、A-NFR の計測値。「次の 3 項目」と「未検証の前提」の更新は含めない)、付録 H への追記、DEMO-LOG への追記、Q1〜Q7 の回答の記録に限る (小さく、理解負債を生まないので、実装を止める理由にしない。8 章 3 の 1 日 5 本と 8 章 5 の比率の集計にも数えない)。ADR・PRODUCT.md・ACCEPTANCE.md の改訂と revert の PR は、`docs` ラベルでも本数に数える。
3. **承認ゲート**: マージにはオーナーの承認が要る。オーナーが PR ごとに承認し (チャットでの指示でよい)、その指示を受けてエージェントがマージしてよい。承認の無い PR を、エージェントはマージしない。マージは 1 日 5 本までとし、週次スクリプトで数える。フェーズの ADR、骨格の型の一覧、フェーズの完了はオーナーが承認する。
4. **構造変更チケット**: 構造だけを変える変更 (改名・分割・移動・抽象の追加) には、`structure` ラベル付きの GitHub Issue で次の 4 点をそろえ、オーナーの事前承認を得る。機能 PR の中での整理は、同じファイル内で 100 行以内ならチケット不要。
   - それを必要とする失敗テストか計測値
   - 「今の構造で何が壊れるか」を書いた 1 枚のメモ
   - 触るファイルの一覧
   - タイムボックス
5. **比率と進捗の監視**: PR のラベル (feat / fix / port / structure / docs / ci / test / spike) から週ごとの比率を、週次のスクリプトで集計し、STATUS の「現況」欄に直近 4 週分を置く。Phase 2 の最初の 3 本 (事前承認済みの structure PR) と、撤退時の復元 PR は集計から除く。structure が 2 週続けて 30% を超えたら、翌週は structure の PR を止める。週ごとに「新しく green になった受け入れ ID の数」も同じ欄に記録し、2 週続けて 0 件なら止めてオーナーと再計画する (ラベル比率の週次スクリプトを main に入れた翌週から数える。骨格再建では Phase 2 のメタ検査 PR、止血案では撤退の手順 2 で入る。Phase 2〜4 から撤退した場合は、復元 PR の翌週から数え直す)。
6. **骨格の凍結**: 本 ADR と ADR 021 の決定は v0.5 まで変えない。変えるには、ADR の改訂、オーナーの承認、構造変更チケットの 3 点をそろえる。同じサブシステムの方式転換は 3 か月に 1 回までとする。ADR 021 で凍結した後のスキーマへの追加だけの変更は凍結の変更に当たらず、ADR の改訂は要らない。移行の段と移行テストは v0.2 以降の変更で必須とする (5 章「保存」)。5 章「画素の正本」で事前に決めた GPU 代替の発動は、本 ADR で決めた分岐なので方式転換に数えない。
7. **自動化**: コードを変更する多エージェントの自動バッチは禁止する。調査・レビュー・計測には使ってよい。実装は 1 セッション 1 PR とする。
8. **完了の定義**: 受け入れ ID のテストが green で、かつオーナーの実機デモ (DEMO-LOG に記録) に合格したら完了とする。テスト件数・clippy 0・grep 0 件は完了条件にしない。完了条件はフェーズの開始時に確定して後から書き換えず、未達は未達として記録する。見積もりの 150% を超えたら止めて再計画する (Phase 1 では、事前に決めた延長を除いた暦で判定し、達した時点で 6 章 Phase 1 の「Phase 1 の期限」の手順を始める)。
9. **トランク運用**: main 1 本で運用する。ブランチは作成から 3 日以内に PR を出すか削除する。WIP コミットで退避したブランチも同じ期限に従う。例外は、PR の base にするための `spike-base` (Phase 1 の終わりまで) だけとする。PR はオーナーのレビュー待ちの間は開いたままでよい (待ちの量は 8 章 2 の上限 3 本で抑える)。未コミットの作業は 1 日以内に片付ける。長く残す必要がある記録 (旧コード、ADR 019 の WIP、再現テスト) はブランチではなくタグで残す。マージのたびに main が動く状態を保ち、週 1 回と各フェーズの終わりにタグを打つ。例外は Phase 2 の撤去 PR から最初のデモまでの期間で、このあいだの「動く状態」は 6 章 Phase 2 の読み替え (撤去 PR から骨格 PR までは「メタ検査 CI が green」、骨格 PR からは「gate が green」) に従う。Phase 0〜1 は gate がまだ無いので、README-LEGACY.md の手順でビルドとテストが通ることを「動く状態」とみなす。Cargo.lock はコミットし、alpha 版の依存は `=` で固定する。
10. **ADR**: 状態 (Proposed / Accepted / On-hold / Superseded-by NNN / Abandoned)、作業日時、モデル名を必須にし、CI で欄の有無を検査する。決定を覆すときは、同じ PR で古い ADR の状態も更新する。本体と分冊に分けた ADR (020 など) では、分冊の状態欄は本体への参照でよい。付録は欄の検査の対象にしない。
11. **文書の上限**: 文書は README.md、CLAUDE.md、`.github/` の PR テンプレート、docs/PRODUCT.md、docs/ACCEPTANCE.md、docs/ARCHITECTURE.md (300 行以内)、docs/STATUS.md (150 行以内。現況、次の 3 項目、未検証の前提、再開手順、運用の変更 (8 章 2 の調整値の写し (正本は付録 H) など。最新の値と日付だけを置き、古いものは git の履歴に任せる)、試行期間の実測値と見積もりの計算、A-NFR の計測値)、docs/adr/ (索引の README.md を含む)、docs/DEMO-LOG.md (1 件 10 行以内) だけにする。例外として、README-LEGACY.md と、7 章で「Phase 2 の撤去 PR」で捨てるとした文書一式 (旧 ARCHITECTURE.md を含む) は、撤去 PR まで置いてよい。コードのコメントに BL- / Phase / 「旧」を書かない。
12. **テスト**: 本番と同じ経路を通す。GPU が無ければ失敗させる (環境変数を指定したときだけ飛ばす)。catch_unwind は禁止し、CI の grep で検査する。受け入れテストは Driver だけを使う。Driver はパネルのヘッドレス実行 (Blitz の DOM と Wasm) を内包し、UI の受け入れテスト (A-R12a〜d など) も Driver の語彙で書く。実装前にテストが失敗したログを PR に残す。gate スクリプトは、同梱パネルの Wasm ビルド (wasm32。Phase 2 で最初の Wasm パネルを入れる PR から。パネルを読み込むテストはビルド済みの .wasm を使うため)、`cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`、依存規則テスト、catch_unwind の grep、期待失敗の照合、を順に実行する。未実装の受け入れテストは `#[ignore = "expected-fail: A-xx"]` を付けて置き、`cargo test` を赤にしない。gate は ignore 付きのテストを別に実行し、失敗したテストの集合が期待失敗リストと一致することを確かめる。期待失敗リストは、ACCEPTANCE.md で「テスト作成済み・未達」とした ID だけとし、「テスト未作成」の ID は照合の対象にしない。
13. **移植**: legacy-final タグから 1 PR に 1 部品ずつ移植する (例外は 7 章の「移植 (例外)」の行に挙げた ADR 019 の WIP で、移植元は `legacy-adr019-wip` タグ)。「部品」は 800 行 (8 章 1 の移植 PR の上限) に収まるモジュールとする。これを超えるものは分ける。例えば pen-io は bytes / abr / gbr / sut / pen_format / pen_catalog の単位、presenter はパイプラインごとと present_quads のビルダごとに、panel-html は view のモジュール (dom / layout / present / actions) ごとに分ける。PR には元のパスとコミット、変えた前提、持ち込んだテストを書く。対象は旧コードのドメイン型に依存しない葉に限る。ただし、座標や矩形の型 (`KomaBounds` など) への依存を新しい geom の型に差し替えるだけで済むものは、移植してよい (例: `features/koma/gesture.rs`)。
14. **ドッグフーディング**: Phase 2 の 2〜3 週目からは毎週、エージェントが動くものをオーナーにデモする。Phase 2 以降はフェーズごとに、Phase 5 以降は毎週、オーナーが新しいアプリで描く。見つけた不具合は先に受け入れテストにしてから直す。
15. **中断と再開**: 2 週以上空いた後に再開するときは、まず STATUS の「再開手順」に従って gate を回す。オーナーが規約と次の 3 項目を確認してから実装を再開する。
16. **機械的な強制は行わない**: ブランチ保護、rulesets、hooks、追記専用ログ、週次の監査と、それらの試験は入れない (2026-10-14 のオーナーの判断。10 章 Q3 の部分不受理)。個人開発の勢いを削ぐ割に、エージェントの動作の歯止めとして大して効かず、有害だと判断したためである。初版は、これらを Phase 0 で入れると定めていた。付録 G (強制の設計) は PR #17 で足したが、同じ判断で取り下げた (git の履歴に残る)。規約は、CLAUDE.md、PR ごとのオーナーの承認 (8 章 3)、メタ検査 CI (8 章 1) で守る。CI の検査は段階を追って入れる。Phase 0 で行数・ファイル数・ID の参照 (8 章 1)、Phase 1 のスパイクの PR から fmt・clippy・test (6 章 Phase 1。コードを含む PR には必ず付ける)、Phase 2 の骨格 PR で gate と依存規則テスト (禁止依存とクレート数)、Phase 2 のメタ検査 PR で ADR 欄である。ラベル比率は CI ではなく週次スクリプトで集計する (8 章 5)。
17. **オーナーの時間は記録しない**: オーナーは、レビュー・デモ・文書にかかった時間を記録せず、週ごとの申告もしない。レビューの速さを週ごとに集計して監視することもしない (2026-10-13 と 14 のオーナーの判断。記録や集計の手間が、得られるものに見合わないためである)。見積もりは、Q2 の回答 (週 8 時間以上) を前提とする。レビューが追いついているかは、Phase 1 の出口ゲートと Phase 2 の 3 週目の関門で、その時点の GitHub の記録から確かめる (6 章)。そこで使う「レビュー完了までの日数」は、コードを含む PR (8 章 1 で行数を数える対象のファイルを変更する PR) の作成から、マージまたはクローズまでの日数とする。確かめる時点でまだレビュー待ちの PR は、その時点までの日数で数える。文書の維持にかかるオーナーの時間は週 1 時間以内を目安にし (記録はせず、オーナーの実感で判断する)、Phase 2 の終わりに規約が重すぎないかを見直す。重すぎる場合は、5 (比率の集計) → 11 (文書の行数の上限と許可リスト) の順に緩める。これらを緩めるのは方針の変更なので、本 ADR の改訂と 11 章 1 の再レビューを要する。1・3・7・8・12 (レビュー単位、承認、自動バッチの禁止、完了の定義、テスト) は根本原因に直接対応するので、規約の重さを理由に緩めない。これらを変えるには、10 章 Q3 の部分不受理による改訂か、同じ根本原因への別の手当てを示した本 ADR の改訂と 11 章 1 の再レビューを要する。誤検知を直す細目の変更 (8 章冒頭) はこの制限に当たらない。

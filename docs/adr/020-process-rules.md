## 8. プロセス規約

**方針と細目の境界**: 規約を運用文書 (CLAUDE.md、PR テンプレート、`.github/` の CI とスクリプト、hooks、STATUS の再開手順と期待値) に落とし込んだ後の正本を次のように分ける。境界は、各運用文書を入れた時点からその文書について効く (Phase 0 のダミー PR の試験で検査の実装を直すのに、本 ADR の改訂は要らない)。本章に書いた正規表現やパスの一覧は初期値である。止血案へ切り替えた場合は、止血案の ADR にも同じ規則を当てる。
- **方針** (本 ADR が正本): 8 章の数値 (上限・閾値・期限)、規約の追加・削除・緩め、8 章 16 の本文 (「本文の確定」に挙げた 5 項目)、6 章の撤退の手順の各段階 (何をどの順で行うか)。変更には本 ADR の改訂と 11 章 1 の再レビューが要る。例外として、8 章 2 の「3 本」は、Phase 1 の判定時と Phase 2 の終わりの見直し時にかぎり、オーナーが実測に基づいて調整してよい。調整した値と理由は付録 H「運用記録」(`020-appendix-audit.md`) に追記し (11 章 1 の再レビューの対象外。Q の回答の記録と同じ扱い)、CLAUDE.md の規約の節と STATUS の「運用の変更」欄の写しにも反映する。調整した後は、付録に追記した値を正本とし、本文の「3 本」は初期値として読む。Phase 1 の出口ゲートは初期値の 3 本で判定する。
- **細目** (運用文書が正本): 検査の実装 (正規表現、数えるパス、スクリプト)、git コマンドの書き方、PR テンプレートの文面。変更は通常の PR で行い、本 ADR は改訂しない。ただし、数える対象を減らす変更、免除の範囲を広げる変更、照合を弱める変更は「緩め」とみなし、方針の手続きで行う。「緩め」は、本 ADR の規則と初期値が対象とする範囲より検査を弱める変更を指す。実装が規則の意図からずれていたのを直す変更 (誤検知や検知漏れの是正) は細目とし、PR 本文に誤検知か検知漏れの実例を書く。hooks はリポジトリの外にあり、エージェントからの編集を hooks 自身で拒否しているので、細目であってもオーナーが直接変え、STATUS の「運用の変更」欄に記録する。

1. **PR の単位**: 1 課題 1 ブランチ 1 PR。手書きのソースの追加・変更行は 400 行以内 (移植 PR は 800 行以内、削除行は対象外)、変更ファイルは 15 以内。受け入れ ID か不具合 ID を 1 つ以上参照する。この 3 点は CI で検査する。検査の定義は次のとおり。
   - 行数を数えるのは手書きのソースだけとする: `*.rs`、`*.wgsl`、`*.toml` (Cargo.lock を除く)、パネルの `panel.html` と `panel.css`、`.github/` の yml と `.github/scripts/**` (gate スクリプトもここに置く)、`scripts/`。テスト (別ファイルの `tests/`、`tests.rs`、`*_tests.rs` に置く規則とする)、文書 (`*.md`、`docs/`)、Cargo.lock、生成物、バイナリ (golden 画像など) は数えない。
   - 移植 PR の 800 行は、PR 本文に `Ported-from: <legacy-final|legacy-adr019-wip>:<パス>` がある場合だけ適用する。
   - 不具合 ID は GitHub Issue の番号とする。受け入れ ID は ACCEPTANCE.md の ID (A-R1 など) とする。スパイクには A-SPK-a〜e を採番する。
   - ID は PR 本文に `Refs: A-R1` や `Refs: #12` の形で書く。CI は正規表現 `^Refs: (A-[A-Za-z0-9-]+|#[0-9]+)` に一致する行を 1 つ以上求め、A- の ID は ACCEPTANCE.md に存在することを確かめる。
   - ID の参照を免除するのは、変更が `docs/` と `*.md` だけの PR、変更が `.github/` だけの PR (CI 用のスクリプトは `.github/scripts/` に置く)、ACCEPTANCE.md ができる前の Phase 0 の PR に限る。CI は変更パスから判定し、ラベルでは免除しない。
   - 変更が `docs/` と `*.md` だけの PR は、ファイル数の上限も免除する (ADR 001〜019 の状態欄の一括更新など)。
   - メタ検査 CI は全 PR で起動する (8 章 16)。
   - 上限の免除はオーナーだけが付けるラベルで行う。`size-exempt` は行数とファイル数の両方を、`files-exempt` はファイル数だけを免除する。`size-exempt` は Phase 2 の撤去 PR と撤退時の復元 PR に、`files-exempt` は Phase 2 の骨格 PR に限って使う (6 章)。
2. **レビュー待ちの上限**: オーナーのレビュー待ちの PR が 3 本 (初期値。8 章冒頭の例外の時期にかぎりオーナーが調整できる) になったら、エージェントは新しい実装を止め、調査と下書きだけを行う。本数に数えないのは「記録だけの PR」、すなわち STATUS の更新 (8 章 11 の欄のうち「運用の変更」、「再開手順」、「現況」の週次の比率と新しく green になった受け入れ ID の数、レビューの追従の値、試行期間の実測値と見積もりの計算、A-NFR の計測値。「次の 3 項目」と「未検証の前提」の更新は含めない)、監査スクリプト側の期待値ファイルの更新 (PR の変更がそのファイルと STATUS だけの場合)、付録 H への追記、DEMO-LOG への追記、Q1〜Q7 の回答の記録に限る (小さく、理解負債を生まないので、実装を止める理由にしない。8 章 3 の 1 日 5 本と 8 章 5 の比率の集計にも数えない)。ADR・PRODUCT.md・ACCEPTANCE.md の改訂と revert の PR は、`docs` ラベルでも本数に数える。この扱いは Q7 の採否にかかわらず適用する。
3. **承認ゲート**: マージにはオーナーの承認が要る。Q7 で別アカウントを使う場合は 8 章 16 のブランチ保護で強制し、承認後のマージ操作はエージェントのアカウントが行ってよい。使わない場合はマージをオーナーが行う。マージは 1 日 5 本までとし、週次スクリプトで数える。フェーズの ADR、骨格の型の一覧、フェーズの完了はオーナーが承認する。
4. **構造変更チケット**: 構造だけを変える変更 (改名・分割・移動・抽象の追加) には、`structure` ラベル付きの GitHub Issue で次の 4 点をそろえ、オーナーの事前承認を得る。機能 PR の中での整理は、同じファイル内で 100 行以内ならチケット不要。
   - それを必要とする失敗テストか計測値
   - 「今の構造で何が壊れるか」を書いた 1 枚のメモ
   - 触るファイルの一覧
   - タイムボックス
5. **比率と進捗の監視**: PR のラベル (feat / fix / port / structure / docs / ci / test / spike) から週ごとの比率を、週次のスクリプトで集計し、STATUS の「現況」欄に直近 4 週分を置く。Phase 2 の最初の 3 本 (事前承認済みの structure PR) と、撤退時の復元 PR は集計から除く。structure が 2 週続けて 30% を超えたら、翌週は structure の PR を止める。週ごとに「新しく green になった受け入れ ID の数」も同じ欄に記録し、2 週続けて 0 件なら止めてオーナーと再計画する (ラベル比率の週次スクリプトを main に入れた翌週から数える。骨格再建では Phase 2 のメタ検査 PR、止血案では撤退の手順 2 で入る。Phase 2〜4 から撤退した場合は、復元 PR の翌週から数え直す)。
6. **骨格の凍結**: 本 ADR と ADR 021 の決定は v0.5 まで変えない。変えるには、ADR の改訂、オーナーの承認、構造変更チケットの 3 点をそろえる。同じサブシステムの方式転換は 3 か月に 1 回までとする。ADR 021 で凍結した後のスキーマへの追加だけの変更は凍結の変更に当たらず、ADR の改訂は要らない。移行の段と移行テストは v0.2 以降の変更で必須とする (5 章「保存」)。5 章「画素の正本」で事前に決めた GPU 代替の発動は、本 ADR で決めた分岐なので方式転換に数えない。
7. **自動化**: コードを変更する多エージェントの自動バッチは禁止する。調査・レビュー・計測には使ってよい。実装は 1 セッション 1 PR とする。
8. **完了の定義**: 受け入れ ID のテストが green で、かつオーナーの実機デモ (DEMO-LOG に記録) に合格したら完了とする。テスト件数・clippy 0・grep 0 件は完了条件にしない。完了条件はフェーズの開始時に確定して後から書き換えず、未達は未達として記録する。見積もりの 150% を超えたら止めて再計画する (Phase 1 では、事前に決めた延長を除いた暦で判定し、達した時点で 6 章 Phase 1 の「Phase 1 の期限」の手順を始める)。
9. **トランク運用**: main 1 本で運用する。ブランチは作成から 3 日以内に PR を出すか削除する。WIP コミットで退避したブランチも同じ期限に従う。例外は、PR の base にするための `spike-base` (Phase 1 の終わりまで) と、8 章 16 の試験用のダミーのブランチ (試験の後に削除) だけとする。PR はオーナーのレビュー待ちの間は開いたままでよい (待ちの量は 8 章 2 の上限 3 本で抑える)。未コミットの作業は 1 日以内に片付ける。長く残す必要がある記録 (旧コード、ADR 019 の WIP、再現テスト) はブランチではなくタグで残す。マージのたびに main が動く状態を保ち、週 1 回と各フェーズの終わりにタグを打つ。例外は Phase 2 の撤去 PR から最初のデモまでの期間で、このあいだの「動く状態」は 6 章 Phase 2 の読み替え (撤去 PR から骨格 PR までは「メタ検査 CI が green」、骨格 PR からは「gate が green」) に従う。Phase 0〜1 は gate がまだ無いので、README-LEGACY.md の手順でビルドとテストが通ることを「動く状態」とみなす。Cargo.lock はコミットし、alpha 版の依存は `=` で固定する。
10. **ADR**: 状態 (Proposed / Accepted / On-hold / Superseded-by NNN / Abandoned)、作業日時、モデル名を必須にし、CI で欄の有無を検査する。決定を覆すときは、同じ PR で古い ADR の状態も更新する。本体と分冊に分けた ADR (020 など) では、分冊の状態欄は本体への参照でよい。付録は欄の検査の対象にしない。
11. **文書の上限**: 文書は README.md、CLAUDE.md、`.github/` の PR テンプレート、docs/PRODUCT.md、docs/ACCEPTANCE.md、docs/ARCHITECTURE.md (300 行以内)、docs/STATUS.md (150 行以内。現況、次の 3 項目、未検証の前提、再開手順、運用の変更 (監査の期待値、hooks のハッシュ、8 章 2 の調整値の写し (正本は付録 H)。期待値の本体は監査スクリプト側のファイルに置いて参照だけにしてもよい。最新の値と日付だけを置き、古いものは git の履歴に任せる)、レビューの追従の値 (直近 4 週)、試行期間の実測値と見積もりの計算、A-NFR の計測値)、docs/adr/ (索引の README.md を含む)、docs/DEMO-LOG.md (1 件 10 行以内) だけにする。例外として、README-LEGACY.md と、7 章で「Phase 2 の撤去 PR」で捨てるとした文書一式 (旧 ARCHITECTURE.md を含む) は、撤去 PR まで置いてよい。コードのコメントに BL- / Phase / 「旧」を書かない。
12. **テスト**: 本番と同じ経路を通す。GPU が無ければ失敗させる (環境変数を指定したときだけ飛ばす)。catch_unwind は禁止し、CI の grep で検査する。受け入れテストは Driver だけを使う。Driver はパネルのヘッドレス実行 (Blitz の DOM と Wasm) を内包し、UI の受け入れテスト (A-R12a〜d など) も Driver の語彙で書く。実装前にテストが失敗したログを PR に残す。gate スクリプトは、同梱パネルの Wasm ビルド (wasm32。Phase 2 で最初の Wasm パネルを入れる PR から。パネルを読み込むテストはビルド済みの .wasm を使うため)、`cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`、依存規則テスト、catch_unwind の grep、期待失敗の照合、を順に実行する。未実装の受け入れテストは `#[ignore = "expected-fail: A-xx"]` を付けて置き、`cargo test` を赤にしない。gate は ignore 付きのテストを別に実行し、失敗したテストの集合が期待失敗リストと一致することを確かめる。期待失敗リストは、ACCEPTANCE.md で「テスト作成済み・未達」とした ID だけとし、「テスト未作成」の ID は照合の対象にしない。
13. **移植**: legacy-final タグから 1 PR に 1 部品ずつ移植する (例外は 7 章の「移植 (例外)」の行に挙げた ADR 019 の WIP で、移植元は `legacy-adr019-wip` タグ)。「部品」は 800 行 (8 章 1 の移植 PR の上限) に収まるモジュールとする。これを超えるものは分ける。例えば pen-io は bytes / abr / gbr / sut / pen_format / pen_catalog の単位、presenter はパイプラインごとと present_quads のビルダごとに、panel-html は view のモジュール (dom / layout / present / actions) ごとに分ける。PR には元のパスとコミット、変えた前提、持ち込んだテストを書く。対象は旧コードのドメイン型に依存しない葉に限る。ただし、座標や矩形の型 (`KomaBounds` など) への依存を新しい geom の型に差し替えるだけで済むものは、移植してよい (例: `features/koma/gesture.rs`)。
14. **ドッグフーディング**: Phase 2 の 2〜3 週目からは毎週、エージェントが動くものをオーナーにデモする。Phase 2 以降はフェーズごとに、Phase 5 以降は毎週、オーナーが新しいアプリで描く。見つけた不具合は先に受け入れテストにしてから直す。
15. **中断と再開**: 2 週以上空いた後に再開するときは、まず STATUS の「再開手順」に従って gate を回す。オーナーが規約と次の 3 項目を確認してから実装を再開する。
16. **機械的な強制** (設定はオーナーが行う)
   - **想定する相手**: 協力的だが、規約を踏み外しうるエージェントとする (6 月の自動バッチのような、悪意の無い逸脱)。敵対的に抜け道を探すエージェントへの防御は、本 ADR の範囲外とする。エージェントはオーナーと同じ OS ユーザーで動き、オーナーの認証情報に触れられるので、完全に防ぐには OS レベルの隔離 (別ユーザーやコンテナでの実行) が要るためである。強制の目的は「代表的な経路では守る結果を起こせないこと」と「起きたら週次の監査で気づけること」の 2 つとし、経路の網羅は目指さない。列挙に無い経路は、見つけ次第「検知漏れの是正」(8 章冒頭の細目) として塞ぐ。
   - **守る結果** (いずれも、エージェントのセッションによって起きることを指す。本 ADR がオーナーの操作と定めた変更 (保護や必須チェックの設定と差し替え、hooks の直接の変更など) は含まない):
     1. main と `spike-base` (Phase 1 の間) に、オーナーが承認した内容以外が入ること (承認の後に追加された push を含む)。
     2. 免除ラベル (`size-exempt`、`files-exempt`) がオーナー以外によって付けられること。
     3. ブランチ保護・タグ保護・リポジトリ設定 (Actions の権限設定を含む) が変わること。
     4. 保護したタグ (`legacy-*`、`archive/*`、`spike-archive/*`、`rebuild-partial`。main から到達できないコミットを指すか、撤退時の参照点になるタグ) が削除・強制更新されること。
     5. hooks と追記専用ログが無効化・編集されること (hooks 自身によるログへの追記は除く)。
     6. 認証情報が切り替えられたり取り出されたりすること (`gh auth switch`、`gh auth token`、資格情報の読み出し)。Q7 で別アカウントを使う場合は、altpaint に対する操作でオーナーの認証情報が使われることも含む。
   - **構成の原則**:
     - **エージェントの身元 (10 章 Q7)**: 推奨はエージェント専用の GitHub アカウント (write 権限だけ、admin なし) で、PR はすべてこのアカウントが作る。オーナーが起点となる main への変更 (STATUS の期待値やハッシュ、hooks の変更の記録、逸脱時の記録と revert など) も、オーナーが値や指示をエージェントに渡し、エージェントのアカウントが PR を作ってオーナーが承認する形で入れる (GitHub では PR の作成者が自分の PR を承認できないため)。8 章 2 の「記録だけの PR」はレビュー待ちの本数に数えない。Q7 で別アカウントを使う場合、エージェントの資格情報は altpaint のセッションにだけ効く場所に置く。Q7 で別アカウントを使わない場合は、誰が PR を作ってもよく、マージはオーナーが行う。
     - **GitHub 側で保証できるものは GitHub 側で保証する** (Q7 で別アカウントを使う場合): 守る結果 1 はオーナーの承認必須のブランチ保護 (最後の push に対する承認を必須にする設定を含み、バイパス不可) で、4 はバイパスの無いタグの ruleset で、3 は admin 権限を持たせないことで保証する。Actions 経由の逸脱は、既定のワークフロー権限を読み取りだけにし、Actions による PR の作成と承認を禁じ、CI が write 権限を要求するワークフローとオーナー以外が付けた免除ラベルを不合格にすることで塞ぐ。
     - **GitHub 側で守れないものは hooks が唯一の予防策とし、監査で補う** (hooks は Q7 の採否にかかわらず、altpaint を対象とする呼び出しのうち拒否したものを、リポジトリ外の追記専用ログに書く。このログは守る結果 5 の対象である。秘密が混ざらないよう、記録する項目は付録 G で絞る): 守る結果 5 と 6、GitHub 側の保証の前提 (エージェントがオーナーの認証情報を使わないこと)、経路を判定できないツール (ブラウザ操作系、他のセッションやクラウドへの委任、入れ子の `claude`) の altpaint での使用。hooks はリポジトリの外のユーザー設定に置き、原本はオーナーの dotfiles に置く。hooks の不具合と別の機器での入れ直しは、後回しにしない。
     - **実行環境**: altpaint のエージェントのセッションは、付録 G の設定 (hooks とエージェントの資格情報) を入れた機器でだけ動かす。オーナー自身が起動する場合も含め、ほかの環境 (クラウドのセッション、GitHub 上の Claude の連携など) は、付録 G で同等の強制を用意するまで altpaint には使わない。同じセッション内のサブエージェント (8 章 7 の調査や 11 章 1 の再レビュー) は、hooks が効くことを付録 G の試験で確かめたうえで使ってよい。効かない場合は、altpaint のセッションでサブエージェントを起動するツールを hooks で拒否し (付録 G の試験の対象に含める)、Plan のレビュー (11 章 1 の再レビューと、グローバル CLAUDE.md が求める Plan レビューのすべて) は、オーナーが同じ機器で別に起動したセッション (hooks が効く) に plan ファイルのパスを渡して行う。
     - **監査はオーナーが自分の端末で行う**: 設定の読み取りには admin の権限が要るので、エージェントのセッションでは行わない。設定 (ブランチ保護、rulesets の `bypass_actors`、`allow_auto_merge`、Actions の権限) を読み取って STATUS の期待値と照合し (応答に項目が無い場合は不合格とする)、承認とマージの記録 (マージ時の head commit に対するオーナーの承認)、免除ラベルを付けた者、オーナーのアカウントによる操作のうちオーナーが自分で行ったと確認できないものが無いこと、追記専用ログに記録された拒否とログが途切れず改変されていないこと (方法は付録 G)、hooks のハッシュと `disableAllHooks` の不在を確かめる。監査にかかる時間は記録しない。8 章 17 の「文書の維持は週 1 時間以内」の目安からは除く。
     - **Q7 で別アカウントを使わない場合**: 守る結果 1〜4 を GitHub の権限では保証できないので、ブランチ保護は「PR 必須・CI 必須・バイパス不可」とし、マージはオーナーが行う (8 章 3)。この場合、エージェントによる PR のマージ・自動マージの設定、免除ラベルの付与、ブランチ保護・rulesets・リポジトリ設定の変更、保護したタグの削除も、hooks が唯一の予防策になる。CI の免除ラベルの検査は操作者を区別できないので効かず、hooks と追記専用ログで置き換える。守る結果 1 の「承認の後に追加された push」は、オーナーがレビューした head を指定してマージする (head が変わっていればマージが失敗する) ことを予防策とし、試験もこの形に読み替える。守る結果 6 は「切り替えと取り出し」だけに読み替える。監査のうち操作者を区別する項目は、追記専用ログの走査に置き換える。この場合 hooks は、拒否したものに加えて、altpaint を対象とする呼び出しのうち許可したものもすべてログに書き (記録する項目は上と同じく付録 G で絞る)、監査では GitHub 上のマージ・ラベル・設定変更の記録と突き合わせる。
   - **逸脱を見つけたときの対応**: (1) エージェントは新しい実装を止める。(2) 影響を受けた PR・ラベル・設定をオーナーが戻すか、事後にレビューする (main の変更は「エージェントの身元」の手順で入れる)。(3) その経路を細目として塞ぎ、STATUS の「運用の変更」欄に記録する。(2)(3) が終わり、オーナーが STATUS に記録したら再開する。(4) 意図的な回避でしか起こせない経路による逸脱だった場合、または同じ守る結果が 2 回破られた場合は、「協力的な相手」の前提が崩れたとみなし、OS レベルの隔離を扱う ADR を起こし、その承認まで実装を止める。
   - **試験の原則**: Phase 0 で守る結果をそれぞれ、実害の出ない方法で試す。本物の設定は先に読み取りで確かめる。書き込みを伴う試験はダミーのブランチ・タグ・保護規則で行い (本物の main への直接 push と、リポジトリ設定の現在値の再設定だけは、読み取りの後に行う例外とする)、試験の後にオーナーがダミーを片付ける。承認の後に追加 push したダミー PR がマージできないことも試す。hooks が拒否した試みと、GitHub 上に記録が残る操作 (ラベル付与、マージ) が監査で見えることも 1 回確かめる (GitHub が拒否した push は記録が残らないので対象外)。`spike-base` を本物で試すかダミーで試すかは付録 G で決める。ログに記録された拒否は守る結果が破られたことを意味しないが、同じ拒否が繰り返し出たときの扱い (規約の周知か、誤検知の是正か) は付録 G で決める。hooks を変えたとき、別の機器に入れ直したとき、保護の対象や必須チェックを変えたときは、STATUS の期待値を更新し、関係する項目の試験をやり直す。`spike-base` の保護の読み取り確認と試験は、Phase 1 で `spike-base` を作ったときに行う。
   - **強制の設計 (付録 G)**: 具体的な設定値、hooks のパターン、CI の検査、監査のスクリプト、試験の手順、資格情報の置き場所は、Q7 の回答とオーナーのアカウント設定に依存するので、本 ADR では上の原則だけを決める。Phase 0 で Q7 に答えた後、エージェントが `.context/` に下書きし、11 章 1 の手順で再レビューを受けてから、PR で `docs/adr/020-appendix-enforcement.md` (付録 G) として新規に追加する。付録 G のレビューでは、8 章 16 の本文を前提とし (変える必要が出たら本文の改訂として 11 章 1 で扱う)、「想定する相手」の外の経路は ISSUE にしない。Phase 0 の開始から 3 週 (Phase 0 の上限 2 週の 150%) を過ぎてもレビューが収束しなければ、11 章 1 の打ち切りの規則に従う。追加した後は、付録 G は初期設計の記録として更新せず、付録 G の内容を引き継ぐ運用文書 (CI、`.github/scripts/` のスクリプト、hooks の原本、STATUS の再開手順と「運用の変更」欄の期待値。8 章冒頭の運用文書のうち強制に関わるもの) を正本とする。8 章 16 が効き始めるのは、付録 G の設定をオーナーが終えた時点からとし、監査もそこから始める。それまでのマージはオーナーが行う。
   - **本文の確定**: 8 章 16 の本文 (想定する相手、守る結果、構成の原則、逸脱時の対応、試験の原則) は、本 ADR が Accepted になった時点の内容で確定とし (止血案へ切り替えた場合は、止血案の ADR が承認された時点の内容で確定とする)、以後の細目は付録 G と運用文書で扱う。本文を変えるのは、守る結果か原則そのものを変える場合だけとする (8 章冒頭の方針の手続き)。
   - **CI の段階**: CI ジョブを足したり外したりするときは、そのたびにオーナーがブランチ保護の必須チェックを直す。CI の検査は 3 段階で入れる: Phase 0 で行数・ファイル数・ID の参照 (8 章 1) と、付録 G の CI 側の検査、Phase 2 の骨格 PR で依存規則テスト (禁止依存とクレート数)、Phase 2 のメタ検査 PR で ADR 欄。ラベル比率は CI ではなく週次スクリプトで集計する (8 章 5)。
17. **レビューの追従の監視 (オーナーの時間は記録しない)**: オーナーは、レビュー・デモ・文書にかかった時間を記録せず、週ごとの申告もしない (2026-10-13 のオーナーの判断。記録の手間が、得られる値に見合わないためである)。見積もりは、Q2 の回答 (週 8 時間以上) を前提とする。レビューが追いついているかは、GitHub の記録から取れる「レビュー完了までの日数」で見る。これは、コードを含む PR (8 章 1 で行数を数える対象のファイルを変更する PR) の作成から、マージまたはクローズまでの日数である (GitHub の記録では操作者を区別できないので、誰の操作かは問わない)。集計の時点でまだレビュー待ちの PR は、その時点までの日数で数える。Phase 2 から、週次のスクリプトが、その週にレビューを終えた PR と、週の終わりにレビュー待ちの PR を合わせて中央値を取り (Phase 2 の初めからスクリプトを入れるまでは、エージェントが `gh` で読み取る)、STATUS の「レビューの追従の値」の欄に直近 4 週分を置く。Phase 0〜1 の値は、この欄には置かない。スパイク PR の値は、STATUS の「試行期間の実測値と見積もりの計算」の欄に置く (6 章 Phase 1)。古い週は消す (git の履歴に残る)。週あたりにレビューを終えた PR の数と、レビュー待ちが上限 (8 章 2) に達していた日数は、使う時点 (Phase 1 の判定、Phase 2 の 3 週目の置き直し、この規約による見積もりのやり直し) で集計する。Phase 2 以降、この中央値が 2 週続けて 4 日を超えたら、見積もりをやり直す。4 日は、Phase 1 の出口ゲートの 2 日の 2 倍である。出口ゲートの 2 日は、週に 2 回以上のレビューを前提にしている。中央値が 4 日を超えるのは、レビューが週に 1 回前後か、それ以下に落ちたことに当たる。該当する PR が 1 本も無い週は、連続の判定から除く (数えず、連続も切らない)。そのうえで、Phase 2〜4 なら撤退を判定し、骨格を凍結した Phase 5 以降なら範囲を削るか中断するかをオーナーが判定する (6 章「撤退の手順」の、凍結後は撤退しない規則に合わせる)。Phase 0〜1 は PR が少なく値が振れるので、この規則は適用せず、Phase 1 の出口ゲートで判定する。文書の維持にかかるオーナーの時間は週 1 時間以内を目安にし (記録はせず、オーナーの実感で判断する)、Phase 2 の終わりに規約が重すぎないかを見直す。重すぎる場合は、5 (比率の集計) → 11 (文書の行数の上限と許可リスト) の順に緩める。これらを緩めるのは方針の変更なので、本 ADR の改訂と 11 章 1 の再レビューを要する。1・3・7・8・12・16 (レビュー単位、承認、自動バッチの禁止、完了の定義、テスト、機械的な強制) は根本原因に直接対応するので、規約の重さを理由に緩めない。これらを変えるには、10 章 Q3 の部分不受理による改訂か、同じ根本原因への別の手当てを示した本 ADR の改訂と 11 章 1 の再レビューを要する。誤検知を直す細目の変更 (8 章冒頭) はこの制限に当たらない。

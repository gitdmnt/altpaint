## 6. 段階計画

規模感は、オーナーがレビュー・実機デモ・文書に合わせて週 8〜12 時間を使える前提で見積もった。
Phase 2〜4 は審査の指摘 (過密・楽観) を反映して提案値より広げた。
Q6 の回答 (Blitz の継続) を反映して、Phase 2 を 1〜2 週、Phase 4 を 0.5 週、Phase 5 を 1 週広げ、Phase 7 を 1 週縮めた。
Phase 5 以降は根拠が弱い。

| マイルストーン | 累計 (週) | 累計 (目安) |
|---|---|---|
| 試行期間の判定 (Phase 1 終了) | 2.5〜3.5 (事前に決めた延長は最大 +2。150% までの超過と期限の再設定は別に足す) | 約 1 か月 |
| v0.1 保存して再開できる (Phase 3 終了) | 13.5〜20.5 | 約 3〜4.5 か月 |
| 骨格の凍結 (Phase 4 終了) | 19〜29 | 約 4.5〜6.5 か月 |
| v0.2 日常で 1 ページ描ける (Phase 5 終了) | 25〜38 | 約 6〜9 か月 |
| v0.5 MVP (プラグイン以外) (Phase 6 終了) | 35〜53 | 約 8〜12 か月 |
| v0.6 MVP 11 項目すべて (Phase 7 終了) | 38〜59 | 約 9〜13.5 か月 |

オーナーがレビュー・実機デモ・文書に使える時間が前提の半分になれば、全体は 1.5〜2 倍に伸びる。Phase 1 を延長した場合 (事前に決めた延長、150% の規則までの超過、期限の再設定を含む) は、以降の累計にも同じ週数を足す。
最も不確かなのは縦書きテキストとブラシの描き味である。

### Phase 0: 凍結・正本・試行の開始

- **目的**: 旧コードを 1 行も失わずに凍結する。要件・受け入れ条件・決定・規約を git 管理の文書にする。メタ検査 CI を入れ、試行期間の計測を始める。
- **範囲**:

  - オーナーの制作シナリオを聞き、docs/PRODUCT.md にまとめる。中身は SKETCH:53-431 の要件、シナリオ、後回し項目、スコープを削る順番。
  - docs/ACCEPTANCE.md を作る。6 章の受け入れ条件は、既存の ID に当たらないもの (proptest、障害注入、差分保存、塗り残し、外部ブラシの反映、変形、プラグインなど) も含めてすべてに ID を振る。ID は A-R1〜A-R16 (R14 は欠番、R12 は A-R12a〜d)、A-SPK-a〜e、A-SCN-*、A-MVP-01〜11、A-NFR-01〜05 (SKETCH:391-397 の暫定目標 5 項目) を採番する。
  - ADR 001〜019 の状態欄を更新し、docs/adr/README.md に索引を作る。ADR 019 の文書は状態を Superseded-by 020 にして main に入れる (コードの WIP は `legacy-adr019-wip` タグに残し、7 章の「移植 (例外)」の行のとおり、各パネルを移植するフェーズ (Phase 2・4・5・6) で移植する)。
  - SKETCH.md の要件を PRODUCT.md に移し、同じ PR で SKETCH.md を削除する (`legacy-final` タグから参照できる)。
  - STATUS.md の「再開手順」には、Phase 0〜1 の間 (main は旧コードで、新骨格の gate はまだ無い) に中断した場合の手順も書く: README-LEGACY.md の手順でビルドとテストが通ることを確かめ、STATUS の「次の 3 項目」と未完了のダミー PR・スパイク PR を確認してから再開する。

  - PR テンプレートと、最小のメタ検査 CI を入れる。Phase 0 で入れるのは、8 章 1 の 3 点 (差分行数、変更ファイル数、ID の参照) だけとする。残りの入れ場所は 1 つずつに決める: 依存規則テスト (禁止依存とクレート数) は Phase 2 の骨格 PR、ADR 欄の検査は Phase 2 のメタ検査 PR、ラベル比率の集計は CI ではなく週次のスクリプトとする。メタ検査 CI を作ること自体が構造作業に膨らむのを避けるためである。
  - 機械的な強制 (ブランチ保護、rulesets、hooks、監査) は入れない (8 章 16。2026-10-14 のオーナーの判断)。
- **残すもの**: 旧コードの全コードと全履歴 (タグ)、再現テスト (`legacy-repro-*` タグに退避)、SKETCH の要件 (PRODUCT.md へ)、ADR 001〜019 の本文、CLAUDE.md の規約 (TDD、関数型、OS 固有コードの禁止、後方互換を残さない)。

  - 6 章の受け入れ条件がすべて ACCEPTANCE.md の ID を持つ。既存の接頭辞に当たらないものは、フェーズごとの `A-PH<番号>-<連番>` (例: A-PH2-03。SKETCH の検証プロトタイプ P1〜P5 と区別するため) で振る。1 つの R 番号の確認が複数のフェーズに分かれるもの (A-R4、A-R5、A-R12a、A-R12b、A-R12d) は、`A-R4-png` のような下位 ID に分ける。

- **規模感**: 1.5〜2 週。オーナーの作業は 6〜10 時間 (本 ADR を読んで Q1〜Q7 に答える 2〜3 時間、制作シナリオの聞き取り 1 時間、ブランチ整理の確認と `legacy-final` のマージ、文書のレビューを含む)。

### Phase 1: 致命リスクのスパイクと試行の判定

- **目的**: 骨格を書き始める前に、選んだ技術で altpaint に必須の入力・表示・性能が成り立つかを確かめる。同時に、規約とレビュー帯域が回るかを実測する。
- **範囲**: workspace の外の `spikes/` で、1 本 1.5 日以内のタイムボックスで行う。各スパイクは独立した `[workspace]` を持つクレートとし、ルートの旧 workspace の Cargo.toml の `exclude` に `spikes` を加える。各スパイクは、head を `spike/<名前>` ブランチ、base を main から作った `spike-base` ブランチ (Phase 1 の最初にエージェントが作り、Phase 1 の終わりに削除する) とする PR として出す。8 章 1 の上限を超えるスパイクは段に分け、レビュー済みの段を `spike-base` にマージしてから、次の段のブランチを切って PR を出す (`spike-base` は main にマージしない)。1.5 日のタイムボックスはエージェントの作業時間で数え、レビュー待ちは含めない。そのうえで、8 章の差分上限の下でオーナーがレビューする。レビューが返るまでの日数と、週あたりにレビューを終えられる本数を、ここで実測するためである。スパイクの PR には、そのクレートの `cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test` を回す CI のジョブを付ける。コードを含む PR を、これらの検査なしに出さない。実機や GPU が要る確認は、手元で行って結果を PR に書く ((e) の結果が出たら、CI に移せるものを移す)。
  - (a) Blitz のパネルを wgpu キャンバスの上に重ね、Wasm のハンドラ (同梱パネルと同じ仕組み) まで通して、日本語 IME・CJK フォント・スライダー・select・スクロールするリスト・フォーカスを試す。旧コードの panel-html と panel-wasm-host を出発点にしてよい (スパイクのコードは捨てる)。
  - (b) オーナーのペンタブで、筆圧・報告レート・ホバー・消しゴム側・傾き・結合サンプルが取れるかを試す (winit、octotablet など)。
  - (c) fontdb・rustybuzz・swash で縦書きの日本語を 2 行組む。
  - (d) CPU 性能を測る。2894×4093・10 レイヤーで 512×512 の dirty 領域を再合成する時間と、ダブ描画時間。ダブ描画は、直径 5px と 300px のブラシで、ダブ間隔を直径の 10%、1 フレームあたりの移動量を 200 ページ px として測る。
  - (e) GitHub Actions の windows-latest (WARP) と ubuntu (lavapipe) で presenter とパネルの描画 (vello) の golden テストが回るかを試す。
- **残すもの**: 計測値、スクリーンショット、判定結果 (`020-appendix-audit.md` の付録 H「運用記録」に追記する)。
- **捨てるもの**: スパイクのコード (main にはマージしない。`spike/*` ブランチはレビュー後に、先に同じコミットへ `spike-archive/*` タグを打ってから削除する)。
- **受け入れ条件**:
  - (a) IME の未確定文字列が表示され、候補窓が入力位置の近くに出て、漢字かな交じり文を確定できる。スライダーはドラッグ位置の値を返す。テキスト欄に入力中はショートカットが発火しない。select で選んだ値と、リスト項目のクリックがハンドラに届く。パネル上のクリックはキャンバスに届かない。値は、どれも Wasm のハンドラが受け取った値で確かめる。パネルを 3 枚表示した状態で、スライダーをドラッグしている間、ポインタのイベントを受け取ってから、その値を反映したパネルの描画を提出するまでの時間の p95 が 16.7ms 以下である。ui を 1 行変えたときの増分ビルドとテストの時間を記録する (合否の条件にはしない)。
  - (b) 筆圧が 0〜1 の連続値で 100Hz 以上届く。ほかの項目は取れるかどうかを表にしてある。
  - (c) 縦書きの句読点が右上に、長音が縦向きに出る (目視)。
  - (d) 再合成の p95 が 8ms 以下で、再合成の p95 とダブ描画の p95 の和が 16.7ms 以内に収まる。不合格の場合の分類として、ダブ描画の p95 が 8.7ms (16.7ms − 8ms) を超えた場合を「ダブ描画の超過」、再合成の p95 が 8ms を超えた場合を「再合成の超過」とする (5 章「画素の正本」と下の代替の選び方、Phase 2 の P2 もこの分類による)。
  - (e) 2 つの OS で golden テストが走るか、走らない理由と代替手段が記録されている。
  - STATUS.md に試行期間の実測値がある: レビューした PR の数、週あたりにレビューを終えた PR の数 (コードを含む PR、すなわちスパイク PR だけで数える)、スパイク PR のレビュー完了までの日数の中央値 (定義は 8 章 17)、レビュー待ちが上限の 3 本に達していた日数。どの値も GitHub の記録から取る。オーナーは時間を記録しない (8 章 17)。
  - 見積もりを置き直した計算が STATUS.md にある。式は「残りフェーズの見込み PR 数 ÷ 週あたりにレビューを終えた PR の数 = 実績の速さでの必要週数」とし、6 章の規模感と大きいほうを採る。この速さは、レビューだけでなく実装の速さにも左右される。試行期間は PR が少ないので、長めの見積もりになる。見込み PR 数は次の和とする (同じ作業を二重に数えない)。
    - Phase 2〜3 で作り直す区分 (付録 F のうち、desktop の状態・効果モデル、提示の糊層、ドメイン、ペイント、永続化と、パネルとホストの接続の半分) の行数を 400 で割った数。パネルとホストの接続は Phase 2 で最小構成を、Phase 4 で IME の配線を、Phase 5 で残りを作るので、付録 F の行数の半分を Phase 2〜3 の分として数える。付録 F の行数はテストを含む概数である。
    - Phase 2〜3 で移植する葉 (付録 F の移植のうち、Phase 4 以降で移植する pen-io・panel-workspace と、同梱パネルの純ロジックを除く) の行数を 800 で割った数。
    - Phase 2〜3 の新規項目と、付録 F の行数では数えない項目 (Driver、Phase 2 のパネル 2 つ (tool-palette と color-palette の panel.html / panel.css / panel.meta.json の移植。ハンドラの書き直しは、上のパネルとホストの接続の行数に含めて数える)、Wasm パネルのビルドと gate への組み込み、tracing とエラートースト、CI と gate、P2/P4 の計測ハーネス、proptest、2 種類のカメラ、PNG 書き出し、閉じる前の未保存確認など) は、エージェントが 6 章の範囲の項目ごとに見積もった PR 数。
    - Phase 4〜7 は、6 章の範囲の項目ごとにエージェントが見積もった PR 数だけを使う (パネルとホストの接続の残り、同梱パネル・panel-workspace・pen-io の移植、外部パネルの開放はここで数える)。
  - 週あたりにレビューを終えた PR の数は、Phase 1 での置き直しでは、レビューを終えたスパイク PR の数を、最初のスパイク PR を出した日から判定の日までの週数で割って求める (コードの PR が出ない Phase 0 の期間は含めない)。Phase 2 の 3 週目からの置き直しでは、直近 2 週にレビューを終えたコードを含む PR (`size-exempt` の撤去 PR を除く) の数を 2 で割って求める。該当する PR が 3 本未満なら、その値と Phase 1 の値の小さいほうを使う。1 本も無い場合は、Phase 2 の 3 週目の関門 (6 章 Phase 2) の扱いに従い、撤退にならなければ Phase 1 の値を使う。
- **出口ゲート**: 次のすべてを満たしたら、本 ADR を Accepted にする。
  - スパイク (a)(b) が合格している (不合格だった場合は、下記の再試行 (a')(b') が合格している)。(c)(d) は合格しているか、下記の代替を確定して記録している。(e) の結果が記録されている。
  - スパイク PR のレビュー完了までの日数の中央値が 2 日以内である (週に 2 回以上レビューの時間を取れていれば、PR を出してから次のレビューまでの間隔は 2 日前後に収まる、という前提から置いた)。オーナーの時間が足りているかは、時間の記録や申告ではなく、この条件と次の条件で確かめる (8 章 17)。
  - レビュー待ちが上限の 3 本に達していた日数が、試行期間の半分未満である。
  - オーナーが、置き直した見積もりを受け入れる。

  満たさない場合の扱いは次のとおり。
  - (a) が不合格なら、UI 技術を再評価して本 ADR を改訂し、再レビューを受ける。そのうえで、代わりの技術 (第一候補は 5 章「UI 技術」の比較表の 2 行目。全パネルを同じ扱いにする Q6 の回答は保つ) で同じ合格条件のスパイク (a') を行い、合格することを Accepted の条件にする。改訂と (a') を合わせて追加 1 週までとし、1 週以内に合格に至らなければ (a') は不合格とみなす。延長した期間も試行期間の計測に含める。(a) がタイムボックスの中で合否を判定できなかった場合は、時間切れだけでは不合格とせず、Blitz のまま最大 1.5 日延ばして判定する。この延長は (a') の追加 1 週に含め、延長の後に不合格なら、残りの期間で改訂と (a') を行う。
  - (b) で筆圧が取れない、または 100Hz 未満なら、別の手段 (別のクレート、ドライバ設定、Windows Ink の設定) を追加 1 週まで探し、決めた手段で (b) をやり直す (b')。探す期間とやり直す期間を合わせて 1 週以内に合格に至らなければ (b') は不合格とみなす。合格することを Accepted の条件にする。延長した期間も試行期間の計測に含める。
  - (a') または (b') も不合格なら、それ以上は再試行せず、止血案への切り替えをオーナーが判定する。
  - 事前に決めた延長 ((a') と (b') それぞれ追加 1 週まで、両方で最大 2 週) は、8 章 8 の「見積もりの 150% で止める」の基準から除く。Phase 1 は 1〜1.5 週と短く、1 週の延長だけで 150% を超えてしまうためである。
  - (c) が不合格なら、9 章の最悪案 (1 文字ずつ縦に積み、回転表で補う) で進む。Phase 4 の見積もりに 2 週を積み増し、STATUS の「未検証の前提」に載せる。これは本 ADR で事前に決めた分岐なので、11 章 1 の再レビューの対象にしない。
  - (d) は、下側レイヤーの合成キャッシュを使う前提で測る。不合格の中身によって代替を分ける。どちらも正本は CPU のまま残す。
    - ダブ描画が超過した場合 (両方が超過した場合は両方の代替を採る): 5 章「画素の正本」の GPU ストローク描画 (描画中の 1 本を GPU のストロークバッファに描き、StrokeEnd で変わったタイルだけを読み戻して CPU の正本で確定する) を Phase 2 の前に採用する。
    - 再合成が超過した場合: 表示用のプロジェクション (ページ合成結果) を GPU で合成する。CPU の再合成は保存・書き出し・undo のときだけ行う。
    - いずれの場合も Q4 をオーナーが判断し直す。代替を採ったら、Q4 の答えが変わらなくても、5 章「画素の正本」と Phase 2 の範囲・受け入れ条件を改訂し、11 章 1 と同じ手順で再レビューを受ける。代替の改訂の再レビューが収束しないときは、11 章 1 の打ち切りの規則に従う。
  - レビュー完了日数、レビュー待ちのいずれかの条件を満たさない場合、または置き直した見積もりを受け入れられない場合は、止血案へ切り替える (下の「撤退の手順」)。
  - **撤退の費用が最も安いのはこの時点なので、最大の判断点をここに置く。**
  - **Phase 1 の期限** (8 章 8 の 150% の規則をこの形で適用する):
    1. Phase 0 の出口ゲートの承認日から数え、事前に決めた延長 ((a')(b') に使った暦。並行した場合は重なりを 1 回だけ数える) を除いた暦で 2.25 週 (1.5 週の 150%) に達したら、判定を始める。
    2. レビュー完了日数・レビュー待ちの条件を、その時点の実測で判定する。満たさなければ止血案へ切り替える。スパイク PR が 1 本も出ていない場合は、レビュー完了日数に値が無いので、この手順では判定せず、手順 4 で扱う。
    3. (2 で切り替えなかった場合) 完了したスパイクには、通常の扱い (この節の合否と不合格時の扱い) を当てる。
    4. 完了していないスパイク ((d) の代替の改訂と再レビューが終わっていないものを含む) についてだけ、オーナーが期限を 1 回だけ (最大 1 週。新しい期限は通常の暦の日付で決める) 再設定するか、止血案へ切り替えるかを判定する。再設定した期限の中で完了したスパイクにも通常の扱いを当てる。(a')(b') は、再設定した期限を過ぎても、それぞれの 1 週の上限まで続けてよい。再設定した期限でも完了しなければ、止血案へ切り替える。
    5. すべてのスパイクの扱いが決まった時点で、再設定と延長の期間を含む実測で出口ゲートの全条件を判定する。
    6. 再設定した期間は試行期間の計測に含め、6 章冒頭の累計にも足す。判定の結果 (再設定したか切り替えたか、新しい期限、理由) は、付録 H と STATUS の「試行期間の実測値」に記録する。
- **規模感**: 1〜1.5 週。

### Phase 2: 骨格の縦切り (描ける・戻せる・コマを動かせる)

- **目的**: 3 つの決定を動くキャンバスで実証する。SKETCH の検証プロトタイプ P2 (4K キャンバス) と P4 (コマ中心ビューとページ中心ビュー) を行う。
- **範囲**:
  - 最初の 3 本の PR を次の順で入れる。この 3 本は本 ADR の承認で事前に承認されたものとし、構造変更チケット (8 章 4) は要らない。どれも `structure` ラベルを付け、本文に Phase 2 を追跡する Issue を `Refs: #<番号>` で書く。撤去 PR と骨格 PR は、あいだに他の PR を挟まずに続けてマージする。
    1. 撤去 PR: 「旧コードのパス一覧」(下の「撤退の手順」で定義) と、7 章で Phase 2 撤去とした文書を削除し、`.gitignore` を新骨格向けに書き換える。削除と `.gitignore` の書き換えだけの PR なので、`size-exempt` で 8 章 1 の上限を免除する。
    2. 骨格 PR: 空のクレート群 (geom / raster / doc / editor と apps) と CI (Windows と Linux の fmt・clippy・test・依存規則テスト)、gate スクリプト (8 章 12) を入れる。依存規則テストは cargo metadata で禁止依存とクレート数を検査する。GPU テストのジョブ (fallback アダプタ) は、gpu クレートを入れる PR で有効にする。同じ PR で CLAUDE.md のコマンドと構成の節を新骨格向けに書き直す。新規ファイルが多いので `files-exempt` でファイル数の上限だけを免除し、行数の上限は守る。
    3. メタ検査 PR: ADR 欄の検査を CI に入れ、ラベル比率を集計する週次スクリプトを入れる。
  - 撤去 PR の時点で main はしばらく動くアプリを持たない。この期間、8 章 9 の「main が動く状態」は、撤去 PR から骨格 PR までは「メタ検査 CI が green であること」、骨格 PR からは「gate が green であること」と読み替える。撤去 PR から最初のデモ (アプリを起動し、ペンで 1 本描き、undo して、終了する) までを 3 週以内とし、超えたら撤退を判定する。
  - geom / raster / doc / paint / editor / gpu / ui / panel-host / panel-protocol / panel-sdk / panel-macros と apps の最小構成を作る。中身は、Id アロケータ、タイルストア、apply から ChangeSet を返す仕組み、構造共有の undo、f32 サンプル → ダブ → ストロークバッファ → 確定という流れのストローク、下側キャッシュ付きの dirty 再合成、GPU での表示、クリップとしてのコマ (はみ出しフラグ付き)、矩形コマの作成・移動・リサイズ、2 種類のカメラ、パネルとホストの接続の最小構成 (5 章「UI 技術」の作る順序)、同梱パネルのうち tool-palette と color-palette (最小範囲で移植し、ハンドラは新しい Action で書き直す。ほかの同梱パネルと同じく Wasm で動かす。panel-workspace の移植は Phase 5 なので、Phase 2 では panel.meta.json の preset の位置と大きさに固定で置き、ヒット判定もその矩形で行う。移動とリサイズは Phase 5 で入れる)、共有テーマ CSS、Wasm パネルのビルドと gate への組み込み (8 章 12)。
  - Driver、PenSample、tracing とエラートーストも入れる。
- **残すもの (移植)**: 座標の newtype、canvas-geometry、raster::blend とゴールデン (premultiplied 化する)、gesture の状態機械と手ブレ補正、ToolDescriptor と view_policy、presenter のパイプラインと present_quads、readback の行パディング解除、pointer.rs と keyboard.rs の正規化、koma/gesture.rs、パネルの表示と実行 (panel-html、panel-wasm-host、panel-protocol の ABI 定数と names、panel-sdk、panel-macros)、ADR 019 の scissor_of と共有テーマ CSS、Wasm パネルのビルドスクリプト (パネルの一覧はスクリプトに書かず `panels/` の下を走査し、既定を release にする)、tool-palette と color-palette の panel.html / panel.css / panel.meta.json と純ロジック (色空間変換を含む)。
- **捨てるもの**: CPU/GPU の二重バックエンド、CpuCanvasSnapshot、提示の dirty rect 機構、(koma_id, layer_index) キー、コマ寸法のビットマップと relayout、Document 内のセッション、DesktopApp と features/、ServiceRequest の文字列バス、command_effects、panel-runtime の host state の JSON 組み立てと翻訳器。GPU compute のカーネルは legacy-final に参照用として残す。
- **受け入れ条件**:
  - A-R1: ストロークの後にレイヤーを追加・削除・移動しても、正本と表示の両方に画素が残る。
  - A-R2 / A-R7: コマを追加・削除・移動・リサイズしても全レイヤーの画素がバイト単位で変わらず、どの操作も undo できる。
  - A-R3: 重なる 2 本のストロークを描いて undo を 1 回すると、1 本目がバイト単位で残る。
  - A-R6: タップ、最後の点で離す操作、拡大表示中の短い線が、それぞれ 1 つの履歴エントリになる。
  - A-R5 の一般化: 正本の変化が、次のフレームの GPU 表示の読み戻しと一致する。
  - A-R15: 2 コマのページで、入力位置と表示位置が 1 ページ px 以内で一致する。
  - A-R12a / A-R12d の先行確認: Driver からパネルをヘッドレスで動かし、スライダーを 80% 位置までドラッグするとその値が Wasm のハンドラに届き、パネル上のクリックがキャンバスに届かない。
  - proptest: 任意のコマンド列で apply → undo が恒等になり、ID が再利用されない。
  - タイルストアの書込みに障害を注入すると、トーストとログが出る。
  - パネルのハンドラの中で書いた状態を直後に読むと、書いた値が返る。
  - トラップするハンドラを呼ぶとログとトーストが出て、ほかのパネルとキャンバスは操作を続けられる。
  - ChangeSet が触れない区分の状態は、パネルへ送られない。
  - P2: パン・ズームと 5 / 50 / 300px のブラシで、フレーム時間の p95 が 16.7ms 以下 (Phase 2 のパネル 2 つを表示した状態で測る)。
  - P4: ビュー切替が 1 フレームで終わり、はみ出しを許したレイヤーがコマの外にも出る。
- **出口ゲート**:
  - CI が green で、オーナーがペンタブで 10 分間描くデモに合格する。合格基準は、画素の消失 0 件、クラッシュ 0 件、見つけた不具合がすべて Issue 化されていること。
  - オーナーが doc クレートの公開型と AppCommand の一覧を読み、PR で承認する。
  - 3 週目に実測値で見積もりを置き直す (Phase 1 の式を使う)。このとき、直近 2 週のコードを含む PR (レビューを終えたものと、レビュー待ちのもの) の、レビュー完了までの日数の中央値 (定義は 8 章 17) が 4 日を超えていれば、撤退を判定する。該当する PR が 1 本も無い場合 (実装の側が止まっている) は、この関門では判定せず、8 章 5 の「新しく green になった受け入れ ID が 2 週続けて 0 件」の規則で扱う。
  - P2 に落ちたら、5 章「画素の正本」の規則どおり、原因 (Phase 1 の (d) と同じ分類) に応じて試す。どちらの超過でもない原因 (転送や提示など) で落ちた場合は、下の「1 週延長しても落ちたら撤退を判定する」で扱う。試すものは、ダブ描画の超過なら GPU ストローク描画、再合成の超過なら GPU での表示用ページ合成、両方なら両方とする。試したものを採る場合は、Phase 1 の (d) と同じく Q4 をオーナーが判断し直し、5 章と本フェーズの範囲・受け入れ条件を改訂して、11 章 1 と同じ手順で再レビューを受ける。1 週延長しても落ちたら撤退を判定する。見積もりの 150% を超えた時点でも止めて再計画する。
  - 撤退する場合は、下の「撤退の手順」に従う。
- **規模感**: 7〜11 週 (Q6 の回答で、パネルの表示と実行の移植と、パネルとホストの接続の最小構成が加わった)。

### 撤退の手順 (止血案への切り替え)

切り替えの経路は 2 通りある (初日に切り替える経路は、Q1・Q2 の回答 (10 章) で骨格再建の試行を選んだので削除した)。

- **Phase 1 の判定で切り替える**: 手順 2〜4 を適用する (main はまだ旧コードなので手順 1 は不要)。
- **Phase 2〜4 で撤退する**: 手順 1〜4 を適用する。

Phase 4 で骨格を凍結した後は撤退しない。凍結後にゲートを落とした場合は、PRODUCT.md に書いた「スコープを削る順番」に従って範囲を削って進む。

**旧コードのパス一覧**: `legacy-final` で追跡されていたファイルのうち、次のパスの下にあるもの (`git ls-tree -r --name-only legacy-final -- <パス>` で列挙する): `Cargo.toml`、`Cargo.lock`、`rust-toolchain.toml`、`.cargo/`、`.gitignore`、`apps/`、`crates/`、`scripts/`、`tools/`、`pens/`、`tests/`、ルートの追跡データ (`canvas-templates.json`、`workspace-presets.json`、`clippy_output.txt`)、README-LEGACY.md。Phase 2 の撤去 PR が消す範囲と、復元 PR が戻す範囲は、どちらもこの一覧とする (`.gitignore` は撤去 PR で新骨格向けに書き換え、復元 PR で戻す)。Phase 0 以降に足す CI 用・計測用のスクリプトは `.github/scripts/` に置き、この一覧に含めない。

1. **main のコードを旧コードに戻す** (Phase 2 以降の撤退だけ。Phase 1 で切り替える場合は main がまだ旧コードなので不要):
   - main の新骨格に `rebuild-partial` タグを打つ。geom / raster / text などの新クレートは、止血案では workspace に入れず、このタグから必要なときに参照する (旧 `crates/raster` との名前の衝突を避けるため)。
   - 「復元 PR」を 1 本作る。先に、`legacy-final` に無く新骨格で追加した追跡ファイルのうち、`.github/`、`docs/`、`.claude/`、`CLAUDE.md`、`README.md` 以外のものをすべて `git rm` し、次に旧コードのパス一覧を `git checkout legacy-final -- <パス>` で戻す。同じ PR で、7 章で Phase 2 に撤去した文書のうち、手順 3 の規約 11 の読み替えで許可する文書 (旧 ARCHITECTURE.md、MODULE_DEPENDENCIES.md、RENDERING-ENGINE.md、builtin-plugins/、user/) を `legacy-final` から戻し、新骨格向けの ARCHITECTURE.md と置き換える。CLAUDE.md は、規約の節を残し、コマンドと構成の節を旧コード向けに書き直す。そのほかの docs/ と .github/ は戻さない (Phase 0 の成果を保つため)。
   - 同じ PR で、CI を旧コード向けの build・test・clippy に差し替え、新骨格向けの依存規則テストとクレート数の検査を外す。
   - 復元 PR は `size-exempt` ラベル (8 章 1) で上限を免除する。
   - 受け入れ条件: 復元後の main がクリーンな clone から README-LEGACY.md の手順でビルドでき、`cargo test` の件数が README-LEGACY.md の記録と一致する。
2. **止血案に要る仕組みのうち、まだ無いものを入れる** (Phase 1 で切り替える場合も同じ):
   - 旧コード向けの CI (build・test・clippy)。Phase 2 以降の撤退では 1 で入れたものを使う。
   - 旧コード向けの gate スクリプト (`.github/scripts/` に置く)。README-LEGACY.md の手順による Wasm パネルのビルド (.wasm は追跡外で、パネルを読み込むテストがビルド済みの .wasm を要るため)・`clippy -D warnings`・test・catch_unwind の grep を順に実行する。旧コード向けの CI も、最初の段で同じ手順で Wasm パネルをビルドする。旧コードは rustfmt の規則に合っておらず (作業ツリーで 354 か所の差分)、一括整形は 8 章 1 の上限を超え `size-exempt` の対象でもないので、fmt は旧コード向けの gate に入れない。catch_unwind の grep は、下の catch_unwind の撤去を main にマージしてから gate に加える。8 章 15 の再開手順はこの gate を回す。
   - ADR 欄の CI 検査と、ラベル比率を集計する週次スクリプト (Phase 1 で切り替える場合はまだ無い)。
   - 見積もりのやり直しの方法: Phase 1 の式は骨格再建の区分に依存するので使わず、手順 4 で起票する止血案の ADR で、付録 E.2 の作業日数を基準にした方法を定める。GPU の無い CI で旧コードの GPU テストをどう扱うか (8 章 12 の「GPU が無ければ失敗させる」の適用範囲) も、同じ ADR で決める。
   - 止血案の Phase 0 のうち本 ADR の Phase 0 で実施していない項目: 再現テスト (`legacy-repro-gpu` / `legacy-repro-nongpu` タグ) を ignore 付きで main に移植する、GPU テストの catch_unwind を撤去する、blitz 系の依存を `=0.3.0-alpha.2` で固定する、wasm ビルドスクリプトを直す (Linux 版に workspace-layout を加え、既定を release にする)。
3. **付録 E.2 の Phase 1 から実行する**。8 章の規約の適用は次のとおり。
   - そのまま適用: 1〜5、7〜10、15。
   - 適用しない: 13 (移植)。6 のうち骨格の凍結の部分。12 のうち Driver の利用・期待失敗の照合・依存規則テスト (止血案は旧コードのテスト構造のまま進むため)。
   - 読み替えて適用:
     - 6 のうち方式転換の部分 (ADR の改訂・オーナーの承認・構造変更チケットをそろえる、同じサブシステムでは 3 か月に 1 回まで) は、止血案の方式転換 (パネル基盤の判定、核の作り直し、egui への移行) にそのまま適用する。
     - 11 は、許可リストに旧コードを説明する文書 (これらには 300 行の上限を適用しない) (旧 ARCHITECTURE.md、MODULE_DEPENDENCIES.md、RENDERING-ENGINE.md、builtin-plugins/、user/、README-LEGACY.md) を加える。panel-ui-definition/ と refactor/ は撤去済み・完了済みの記録なので、手順 4 の PR で削除する (Phase 2〜4 からの撤退では、復元 PR で戻さない)。
     - 12 は、Driver の利用・期待失敗の照合・依存規則テストを除いて適用する (gate そのものは手順 2 の旧コード向けのものを使う)。
     - 14 のドッグフーディングは、フェーズごとの実施を止血案の Phase 0 から、毎週の実施を止血案の Phase 1 (データ消失の止血) の完了から始める。
     - 17 の「Phase 2 の終わり」は、止血案の Phase 2 の終わりと読む。
     - 16 の CI の段階は、依存規則テストと fmt (手順 2 のとおり、旧コードには当てない) を除いて適用する。
4. 手順 3 に着手する前に、1 本の PR (`docs` ラベル) で次を行う: 止血案の ADR を起票し、11 章 1 と同じ再レビューを受ける (起票から 1 週で収束しなければ 11 章 1 の打ち切りの規則に従う。計画は付録 E.2、本文に手順 3 の読み替え後の規約を持つ。以後の規約の正本はこの ADR とする。以後の運用記録はこの ADR の付録に書く)、本 ADR の状態を「Superseded-by (止血案の ADR 番号)」にして切り替えの理由を記録する、CLAUDE.md の規約の節を読み替え後の規約に合わせる。ADR 019 は Superseded-by 020 から On-hold (保留) に戻し、再開するかどうかは止血案の Phase 2 (パネル基盤の判定) で決める。この判定では Q6 の回答 (Blitz の継続、全パネルを同じ扱いにする) を既定とし、止血案の Phase 2 のタイムボックスの中で R12 群を Blitz のまま直せなかった場合に限って、egui への移行を判定する。

### Phase 3: 保存して再開できる (v0.1)

- **目的**: 自分の絵を保存して、閉じて、また開ける状態にする。
- **範囲**: store (スキーマ v1、差分保存、1 トランザクション、integrity_check)、JobRunner (保存と読込、epoch の検査)、未保存の判定と閉じる前の確認・保存ジョブの待機、ユーザーデータディレクトリの作成、PNG 書き出し (ページ単位とコマ単位)、版付き JSON の設定 (3 状態ローダ、一時ファイルに書いて rename)。

   - PR テンプレートと、最小のメタ検査 CI (8 章 1 の行数・ファイル数・ID の参照) を入れる。`size-exempt` と `files-exempt` のラベルを作る。
   - ダミー PR を 3 本 (行数超過、ファイル数超過、ID なし) 出し、CI が不合格にすることを確かめる。
6. **3 週目〜4 週目の前半: スパイク**: Phase 1 のスパイク (a)〜(e) を 1 本 1.5 日以内 (計 7.5 日以内) で行う。各スパイクは、6 章 Phase 1 のとおり head を `spike/<名前>`、base を `spike-base` とする PR としてレビューを受ける。結果は、スパイクごとに main 向けの記録 PR (`docs` ラベル) で付録 H「運用記録」に記録する。
7. **4 週目の前半: 試行の判定 (オーナー 1 時間)**
   - STATUS に実測値 (6 章 Phase 1 の受け入れ条件に挙げたもの) を書き、同じ節の式で全体の見積もりを置き直す。
   - Phase 1 の出口ゲートに照らして、オーナーが「骨格再建で進む (本 ADR を Accepted にする)」か「止血案へ切り替える」かを決める。
8. **判定の後 (go の場合)**
   - Phase 2 の撤去 PR、骨格 PR、メタ検査 PR をこの順で入れる (6 章 Phase 2 の範囲)。
   - 次に、A-R1・A-R3・A-R6・A-R7 と「ID を再利用しない」「apply → undo が恒等」の失敗テストを先に書く。それから Id アロケータ・タイルストア・apply → ChangeSet・構造共有の undo を最小限に実装する。A-R8 (読込後の undo) は Phase 3 の JobRunner と一緒に書く。
   - 並行して P2 の計測ハーネス (合成した 4K の作品、3 サイズのブラシ、パン・ズームの操作列、フレーム時間の p95 と、ダブ描画・再合成それぞれの p95 の記録) を用意する。

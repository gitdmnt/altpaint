## 0. この ADR の位置づけ

オーナーの問いは次のとおりである。

> 度重なるアップデートとリファクタで設計がめちゃめちゃになった。全部壊して作り直したいが、この量のコードを捨てるのももったいない。問題点を列挙し、作り直すべきか、そうでないならどう直すべきかの方針を策定してほしい。

本 ADR はその答えである。
ただし本 ADR 自体が「多エージェント調査 → 大規模再設計」という、ADR 018 と同じ手順の産物である。
ADR 018 はその手順で 3 日間に 262 コミットの構造変更を生み、機能を 1 つも増やさなかった。
そこで本 ADR は実装を直ちに許可しない。
Phase 0〜1 (約 2.5〜3.5 週) を試行期間とし、規約とオーナーのレビュー帯域が実際に回ることを実測してから本格着手する。

## 1. 結論

全部は壊さない。
壊して新しい workspace で作り直すのは、骨格の 5 つである。

- ドメインモデル
- 状態の所有と変化の伝え方
- 画素ストア
- パネルとホストの接続 (状態の渡し方、入力の配線、操作の受け取り)
- 保存スキーマ

旧コードのドメイン型に依存しない部品 (約 15.5〜16k 行、Rust 45k 行の約 35〜36%) は、テスト付きで 1 つずつ移植する。
そのうち約 11k 行は、動作とテストで検証済みの部品である。
残りの約 4.5〜5k 行 (パネルの表示と Wasm の実行) は、Q6 でパネルの方式 (Blitz と Wasm) を続けると決めたので、R12 の入力まわりを直しながら移植する。
作り直すのは約 17〜19k 行である (内訳は付録 F)。
この方式を **「骨格再建・選別移植方式」** と呼ぶ。

崩れた主な原因はコードではなくプロセスにある。
プロセスを先に直さなければ、作り直しても同じ崩れ方をする。
そのため Phase 0〜1 で次の 3 点を確かめてから着手する (判定基準は Phase 1 の出口ゲート)。

- 規約 (8 章) が実際に回ること (レビュー待ちが上限に達した日数が試行期間の半分未満)
- オーナーの時間 (レビュー・実機デモ・文書の合計) が足りること (Phase 1 の各週で、確保できると申告した時間が週 4 時間以上あり、スパイク PR のレビュー完了までの日数の中央値が 2 日以内)
- 技術スパイクのうち (a)(b) が合格し (1 回だけ代わりの手段で再試行できる)、(c)(d) は合格するか代替を確定して記録し、(e) の結果が記録されていること

条件を満たせなければ、「止血してから機能を出す」案 (旧コードを局所修正する案、4.3 節) へ切り替える。
その計画は付録 E.2 にあり、切り替えの手順は 6 章の「撤退の手順」に定める。

期間の見込みは、保存して再開できる v0.1 まで約 3〜4.5 か月、日常の制作に使える v0.2 まで約 6〜9 か月である (Q6 の回答を反映した値)。
この見積もりは実測で較正していない。
Phase 1 の終わりと Phase 2 の 3 週目に置き直す。
その間、旧アプリでは描かない前提にする。

## 3. 根本原因

1. **要件と受け入れ条件が無いまま、構造指標を完了基準にした。** 何ができれば「使える」のかが決まっていなかった。そのため作業は構造の整備に向かい、完了条件もすり替わった (26〜28)。
2. **骨格の 3 つの決定を初週のプロトタイプのまま据え置いた。** 状態の所有と変化の伝え方、作品内で一意な ID、コマ・ページ・画素ストアのモデルの 3 つである。その上で周辺の方式 (UI、GPU 化、クレート構成) だけを付け替えたので、付け替えるたびに前提の食い違いが横付けで増えた。典型は、GPU 化の後も CPU 経路が残り R1〜R5 を生んだことである (14〜17)。
3. **方式を計測なしで決め、後で覆した。** Blitz、全パネルの Wasm 化、GPU 必須化はどれも数値の関門を通っていない。全パネルの Wasm 化は、SKETCH:231「標準パネルは MVP ではまず本体モジュール」に初日から反している (19、26)。オーナーは Q6 で、Blitz と全パネルの Wasm 化を続けると決めた。そこで本 ADR は、欠けていた数値の関門をスパイク (a) として先に通す。
4. **レビューできない速度で自動実行し、長寿命ブランチを統合しなかった。** オーナーが読んでいないコードが大半になり、崩れに気づく人がいなかった (29、30)。
5. **テストが本番経路を通らない作りだった。** CPU 経路での検証、GPU 不在時の黙認、catch_unwind、CI 無しが重なり、「576 件 pass」の裏で 16 項目の不具合が失敗テストで再現した (24)。

## 4. 判断の理由

### 4.1 骨格を作り直し、葉を残す理由

- 監査した 8 領域のうち 7 領域が、自領域の中核を「モジュール単位の作り直し」と判定した。対象を足すと約 23k 行で、骨格そのものになる。残るのは葉と配線だけである。その後、オーナーが Q6 でパネルの表示と Wasm の実行を残すと決めたので、作り直しは約 17〜19k 行になった (付録 F)。
- 3 つの欠けた決定は、document-model・gpu-paint・保存スキーマ・履歴・提示・書き出しのすべてに焼き込まれている。その場で差し替えると旧モデルと新モデルが併存する期間が必ず生まれ、その期間は R1〜R5 を生んだ二重正本と同じ構造になる。
- 旧アプリは基本操作で原稿を失う (R1〜R4、R9、R10)。使い続けるには止血が要り、その止血コードの多くは骨格を直すときに捨てることになる。旧アプリの使用状況はコードからは分からない (R11 があるため、`%APPDATA%\altpaint` の有無は使用状況の証拠にならない)。Q1 で、旧アプリでは描いておらず、v0.2 まで描かなくてよいことを確かめた。
- オーナーの「全部壊して作り直したい」と、SKETCH:40 の学習動機にも合う。

### 4.2 全面作り直し (移植なし) を退けた理由

移植する葉は依存が細く、テストも付いている。
移植は 1 部品あたり数日で済む。
対象は pen-io のパーサ 2.4k 行、チャンクコーデック、ブレンドのゴールデン、座標の newtype、色空間変換、presenter のパイプラインなどである。
ゼロから書き直すと、既に解いた境界条件をもう一度踏むことになる。

### 4.3 止血→出荷案を土台にしない理由

オーナー価値の審査はこの案を勝者とした (31/50)。
根本原因の審査は最下位とした (31.5/50)。
本 ADR がこの案を土台にしない理由は 5 つある。

1. 3 つの決定が 3〜4 か月先送りになる。その間、誤ったモデル (コマ寸法キャンバス、index キー) の上にページ・PDF・線質を積むことになる。
2. オーナー価値の審査が挙げた接ぎ木 (egui への早期移行、最終形の ADR の先行確定、縦書きの葉クレート化) を当てると、この案は骨格再建に近づく。接ぎ木後もこの案にだけ残る利点は「旧アプリを使える状態に保つ」ことで、それはオーナーが旧アプリで実際に描く場合にしか価値を持たない。
3. 止血用に書くコードの多く (write-back、R12 のうちパネルとホストの接続の側の補修) は、後の作り直しで捨てることになる。
4. CPU ペイント経路をテスト用に残すので、「テストが本番経路を通らない」構造が長く続く。
5. 両方の審査が、この案の核の作り直し (25〜40 作業日) を楽観的すぎると指摘した。

ただし、この案が勝つ条件は明確にある。
「2〜3 か月以内に実作業で使う必要がある」場合と、「週に割ける時間 (レビュー・実機デモ・文書の合計) が 4 時間未満」の場合である。
どちらかに当てはまれば、この案に切り替える (Q1・Q2)。
規約の精密さ (構造変更チケット、比率の上限、方式転換の頻度制限) は、この案から取り込んだ。

### 4.4 その場の strangler 案を退けた理由

- MVP 到達の期間 (8〜12 か月) は本案とほぼ同じだが、新機能が出ない期間が長い (次項)。
- 核の差し替え (P2〜P4) だけで新機能が出ない期間が 13〜19 週続く (付録 E.3)。これは B0〜B10 (機能 0 のまま 262 コミット) と同じ形である。
- 最大の分岐であるドメインモデルの決定が最後に来る。
- 画素の正本を GPU 常駐にするので、保存・書き出し・スナップショットのすべてが非同期の読み戻しに依存する。

テストの Driver ファサード、見積もりの 150% で停止する規則、ジョブ結果の epoch 検査は、この案から取り込んだ。

## 10. オーナーに決めてもらうこと

回答 (2026-09-23) は、各項目の末尾に記録する。

- **Q1. 目的と期限**: 「実用を完了基準にし、学習は骨格の設計で満たす」でよいか。現在、旧アプリで実際に描いているか。2〜3 か月以内に実作業で使う必要はあるか。v0.2 まで (約 5〜8 か月) 旧アプリでは描かなくてよいか。
  - 推奨既定: 実用を完了基準にし、期限は無く、旧アプリでは描かない。
  - 理由: 旧アプリは最小限の修正をしても R1〜R4 が残り、安全に描けない。
  - 他を選んだ場合: 旧アプリで描いている、または実作業が必要なら、止血案 (付録 E.2) に切り替える。
  - **回答**: 推奨既定どおり。実用を完了基準にし、期限は無く、旧アプリでは描かない。回答の時点の見込みは v0.2 まで約 5〜8 か月で、Q6 の反映で約 6〜9 か月になった。
- **Q2. 時間**: レビュー・実機デモ・文書に、合わせて週何時間使えるか。
  - 推奨既定: 週 8 時間以上 (まとめてレビューする日を週 1 日含む)。
  - 他を選んだ場合: 週 4〜8 時間なら、期間 1.5〜2 倍の見込みで続ける。週 4 時間未満なら止血案を推奨する。長い再建が途中で止まると、作りかけの骨格しか残らないためである。
  - **回答**: 週 8 時間以上。
- **Q3. 規約**: 8 章の規約と、その機械的な強制 (ブランチ保護、CI、hooks、自動バッチの禁止、オーナーの承認によるマージ) を受け入れるか。
  - 推奨既定: 受け入れる。
  - 他を選んだ場合: 一部の規約だけを受け入れない場合は、8 章をその回答に合わせて改訂し、11 章 1 の手順で再レビューしてから進む。規約を全面的に受け入れない場合は、骨格再建も止血案も採らない (止血案も同じ規約を前提にしているため)。その場合は、どう進めるかをオーナーが改めて判断する。
  - **回答**: 受け入れる。
- **Q4. 画素の正本**: CPU タイルを正本にし、GPU を表示専用にしてよいか (SKETCH:524「GPU 中心」からの変更)。
  - 推奨既定: 認める。スパイク (d) か Phase 2 の P2 に落ちたら、5 章の規則どおり原因に応じてプレビュー合成かページ合成を GPU に移す。それより後に性能の不足が分かった場合は、8 章 6 の方式転換として扱う。
  - 他を選んだ場合: GPU を正本にすると、保存・書き出し・undo のすべてに読み戻しと順序の制御が要り、R1〜R5 と同種の不具合が起きやすくなる。
  - **回答**: 認める。あわせて、ダブ描画が遅い場合の代替を「GPU プレビュー合成 (確定は CPU で描き直す)」から「GPU ストローク描画 (描画中の 1 本を GPU のストロークバッファに描き、StrokeEnd で変わったタイルだけを読み戻して CPU の正本で確定する)」に変えた (5 章「画素の正本」)。
- **Q5. コマのデータモデル**: レイヤーをページ座標に置き、コマをクリップとして扱う CSP 型にしてよいか。
  - 推奨既定: CSP 型にする。はみ出し描画・重なり・ページ単位の書き出しを素直に表せる。
  - 他を選んだ場合: コマ独立キャンバスを維持すると、はみ出しとページ合成に別の仕組みが要る。
  - **回答**: CSP 型にする。
- **Q6. UI とプラグイン**: SKETCH の「UI ランタイムを内製する」方針を、「同梱パネルは egui で作り、第三者パネルは Wasm が返す中間表現を egui で描く」に変えてよいか。第三者パネルは Phase 7 (MVP の最後) でよいか。
  - 推奨既定: そのとおりにする (比較は 5 章「UI 技術」)。
  - 他を選んだ場合: SKETCH どおり内製するなら、テキスト入力と IME の自作で Phase 2〜5 が数週ずつ延びるが、学習としての面白さは最も大きい。Blitz を続けるなら、入力配線・IME・select の大改修と alpha 版への依存が残る。
  - **回答**: 推奨以外。同梱パネルと外部パネルを同じ扱いにし、すべてのパネルを HTML + CSS + Wasm (Blitz) で動かす。外部フォルダからの読み込みは Phase 7 (MVP の最後) で開放する。11 章 1 に従って 1 章と 3〜10 章と付録 F を改訂し、再レビューにかけた。

- **Q7. エージェントの GitHub 上の身元**: エージェント専用の GitHub アカウント (write 権限だけ、admin なし) を用意し、エージェントのセッションではそのアカウントの `GH_TOKEN` と git の資格情報を使うか。
  - 推奨既定: 用意する。アカウントの作成と招待はオーナーが行う。
  - 理由: GitHub の権限と記録の上でオーナーとエージェントを区別できるようになり、「マージにはオーナーの承認が要る」「エージェントは設定を変えられない」を GitHub 自身が強制し、監査でも操作者を区別できる (8 章 16)。
  - 他を選んだ場合: 8 章 16 の「Q7 で別アカウントを使わない場合」のとおり、マージはオーナーが行い、操作者を区別する監査を追記専用ログの走査に置き換える。強制は弱くなる。
  - **回答**: 用意しない。8 章 16 の「Q7 で別アカウントを使わない場合」の構成をとり、マージはオーナーが行う。付録 G はこの構成で書く (11 章 1)。

5 章で「確認のみ」とした項目 (テキストの範囲、undo の範囲、パネルの配置方式、対象 OS、同じリポジトリで作業すること、旧原稿を移行しないこと、性能目標、ペン機能の範囲) は推奨既定値で仮置きする。
